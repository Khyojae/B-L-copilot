# JWT 설계

> 출처: 717 멘토님 피드백 회의 발표 자료 (기획: 사용자 인증 접근 권한 구조 설계, 6/27~7/1)

## 목적

여러 기관(화주/선사/포워더/은행/관세청)이 함께 쓰는 플랫폼에서, 요청을 보낸 사람이 누구이고 어떤 권한을 갖는지 매 요청마다 안전하게 증명하기 위함.

## 1) 토큰 구조 (HEADER)

- `alg`: HS256
- `typ`: JWT

## 2) PAYLOAD 설계

| 필드 | 설명 |
|---|---|
| `iss` | 발급 인증 서버 |
| `aud` | 백엔드 API URI |
| `sub` | 사용자 ID |
| `role` | shipper / carrier / forwarder / bank / customs |
| `org_id` | 소속 기관 ID |
| `exp` | 만료 시각 (Access Token: 15분) |
| `iat` | 발급 시각 |
| `jti` | 토큰 고유 ID |

민감정보는 payload에 넣지 않는다.

## 3) 서명 알고리즘: HS256 vs RS256

**HS256 채택.** 이 플랫폼에서 JWT를 검증하는 주체가 항상 우리 백엔드 하나뿐이라서(은행, 관세청도 결국 우리 플랫폼 API를 통해서만 접근 — 토큰을 직접 검증하지 않음) 비밀키 공유 문제가 없음. 만약 향후 aiService 등 다른 서비스가 토큰을 독립적으로 검증해야 하는 상황이 생기면 RS256(비대칭키) 전환을 재검토.

## 4) AT/RT 전략

- **AT(Access Token)**: API 접근 권한 증명. **15분** (인증서·서명 작업 등 데이터 민감도가 높아 짧게 설정)
- **RT(Refresh Token)**: AT 만료 시 재로그인 없이 새 AT 발급. **1일** (노출 기간 최소화 vs 재로그인 부담 사이 균형)
- RT는 DB에 해시로 저장, 로그아웃/재발급 시 폐기(rotation) — [db-schema.md](./db-schema.md)의 `refresh_tokens` 참고

## 5) 보안 유의점

- 전송은 반드시 HTTPS
- 페이로드에 민감정보 금지
- 인증/인가 실패 에러 응답은 뭉뚱그려서 401만 반환 (세부 사유 노출 금지)
- 비밀키(HS256 secret)는 256비트 이상 랜덤값으로 환경변수에 저장
- 검증 시 `iss`, `aud`도 반드시 옵션에 포함해서 확인
