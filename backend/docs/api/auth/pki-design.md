# PKI 전자서명 설계

> 출처: 717 멘토님 피드백 회의 발표 자료

## 목적

개인키/공개키 쌍을 이용해 무역 서류가 위변조되지 않았고, 정당한 기관이 승인했다는 것을 증명.

## 1) 신뢰 구조 (발급 → 서명 → 검증)

중간 CA 단계를 없애고 단순화: **Root CA가 선사 인증서를 직접 발급**한다.
(발급 유형이 선사 하나로 단일하고, 발급 빈도도 낮아 중간 CA의 이점이 없음)

## 2) 키 관리 (2계층)

| 환경 | 저장 위치 |
|---|---|
| 로컬 개발 | `.env` 환경변수 |
| AWS 운영 | AWS Parameter Store (SecureString) |

## 3) 인증서 정책

- **누가 가지나**: 선사만 인증서 보유
- **서명 대상**: e-B/L 원본의 SHA-256 해시 (PDF 파일 바이트 기준)
- **소유권 이전 서명**: 블록체인 지갑(MetaMask) 서명으로 별도 처리 — X.509 인증서 서명과는 다른 경로

## 4) 갱신 정책

- 유효기간: **1년** (SSL/TLS 인증서 업계 표준 참고. 너무 짧으면 갱신 부담, 너무 길면 보안 취약)
- 만료 시 자동 차단 처리

## 5) 암호 알고리즘

- 해시: SHA-256
- 서명 로직: SHA-256 해시 + 개인키 서명 (표준 문서 서명 방식)

## 6) 검증 단계 (구현 순서: 만료 → 체인 → 폐기 → 서명)

1. **만료 확인** — 유효기간(발급 + 1년) 내인가
2. **체인 검증** — 신뢰된 Root CA가 발급한 인증서인가
3. **폐기 확인** — 키 유출 등으로 무효화되지 않았는가 (`certificates.is_revoked`, CRL 대신 이 컬럼으로 단순화)
4. **서명 검증** — PDF의 SHA-256 해시와 서명이 일치하는가 (위변조 여부)

> 설계상으로는 "체인→만료" 순서가 더 자연스럽지만, 실제 구현(`api/src/auth/pki/verify.js`)에서는 **만료를 체인보다 먼저** 확인한다. `node-forge`의 `verifyCertificateChain`이 신뢰 체인 검증과 만료 검증을 분리 못 하고 함께 수행하는데, 만료된 인증서를 체인 검증에 먼저 넣으면 실패 사유가 "만료"가 아니라 "신뢰 안 됨(chain)"으로 뭉뚱그려져 버그처럼 보고된다(실제로 구현 중 발견). 만료를 우리가 먼저 자체 검사해서 걸러내면, 체인 검증에는 항상 "아직 만료 안 된" 인증서만 들어가서 실패 사유가 정확히 나뉜다.

## 7) 라이브러리 선정

검토한 옵션: Node.js 내장 `crypto`, `node-forge`, `pkijs + pvutils`

**선정: `crypto` + `node-forge` 조합**

| 라이브러리 | 역할 |
|---|---|
| `crypto` (Node 내장) | 서명 생성/검증 전담 |
| `node-forge` | CA 인증서 파싱 전담 |

`pkijs`는 제외 — OCSP 실시간 검증, 자체 CA 운영 같은 기능을 이 프로젝트에서 쓰지 않음(Root CA 2계층 단순 발급 구조라 불필요). 학습 비용과 의존성(`pkijs` + `pvutils`)도 더 높음.

> OCSP: 인증서가 지금 이 순간 유효한지 실시간으로 확인하는 프로토콜. 이 프로젝트는 CRL 확인으로 충분하다고 판단해 채택하지 않음.
