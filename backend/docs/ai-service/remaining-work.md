# 잔여 작업 산정 (F1 · F3 · F4)

> 기준일: **2026-08-12**
> 기준 기획안: **`BL_Copilot_기획안_v2.docx`** (최종 수정 2026-08-11)
> 대상: 기획안 5절 핵심 기능 명세의 F1 · F3 · F4
> 측정 대상 커밋: `feature/f1-intake` 작업 트리

이 문서는 설계 문서가 아니다. **기획안 명세와 현재 코드의 차이**를 세고, 남은 작업량을 추정한 기록이다. 설계 근거는 `f1-intake.md` · `f3-defect-prediction.md` · `f4-report.md` 에 있다.

**기준 기획안이 바뀌었다.** 1~14번을 산정할 때 본 것은 1차 설계기획안(2026-08-06)이고, 지금 기준은 v2 다. 5장이 기능별 상세 명세로 확장되면서 **수용 기준**이 생겼고, **10장(실행 범위 및 검증 설계)이 통째로 신설**됐다. 무엇이 달라졌고 그래서 무엇이 새로 열렸는지는 **2.2 절**에 있다.

추정치는 시간이 지나면 틀린다. 재추정할 때는 아래 "측정 방법" 절의 명령을 다시 돌려 수치부터 갱신할 것.

## 1. 현재 진척

| 기능 | 진척 | 상태 |
|---|---|---|
| **F1** 서류 인테이크·초안 작성 | ~95% | 라벨 JSON · 이미지 · PDF · 엑셀 · 이메일 경로 동작. 서류 3종 |
| **F3** 제출 전 하자 예측 | ~95% | 룰엔진·XGBoost 두 축 모두 동작. 8.1 목표 달성, **v2 10.4 성공 판정은 후반 조건 미충족**(2.2) |
| **F4** 선제 대응 리포트 | ~95% | 5개 구성·PDF·LLM·공유 링크 완성 (공유는 v2 10.1 컷라인 **밖**) |

```
aiService 코드  15,250 줄
테스트            471 개 (470 통과, 1 skip)
룰 카탈로그        29 건 / 체크 14 종   (+ 서류 간 10 건)
```

**1~20번이 전건 닫혔다.** 마지막 둘이 이번에 들어왔다 — 18번 스캔 열화 재현
(`ocr/degrade.py`), 19번 수용 기준 실측(`acceptance.py`). 5.12·5.13 절에 있다.

**그러나 "코드가 끝났다"가 "측정이 끝났다"는 아니다.** 19번을 실제로 재 보니
수용 기준 11개 중 **7개 통과·4개 미측정**이고, 미측정 넷은 전부 같은 곳에서
막힌다 — **실물 서류가 없다.** 그중 하나(근거 좌표 보유율)는 실물이 와도
못 잰다는 것이 이번에 드러났다(5.13). 실물 서류와 조문 인용 실무 검증이
여전히 일정의 실제 병목이다.

### 기획안 8.1 정량 목표 대비

> 기획안 8.1: "합성 검증셋 기준 주입 하자 검출 F1-score 0.85 이상"
>
> v2 10.4 성공 판정: "**결합 조건** F1 0.85 이상이며 **룰 단독 대비 개선이 확인될 것**"

5개 시드(42~46) 평균, 2,000건 기준이다. **개발셋과 평가셋의 서류가 겹치지 않는다**(16번 · 5.11).

| 조건 | 구성 | 정밀도 | 재현율 | F1 | 8.1 목표(0.85) |
|---|---|---|---|---|---|
| **균형 50%** | **룰엔진만** | 0.9685 | 0.8625 | **0.9124** | 달성 |
| 균형 50% | 룰 + XGBoost | 0.9413 | 0.8667 | **0.9022** | 달성 |
| **실제 70%** | **룰엔진만** | 0.9729 | 0.9264 | **0.9491** | 달성 |
| 실제 70% | 룰 + XGBoost | 0.9641 | 0.9307 | **0.9470** | 달성 |

**두 비율을 함께 읽어야 한다**(17번 · v2 10.3). 실제 하자율(65~75%)을 재현한 조건에서
F1 이 더 높은 것은 검출기가 좋아진 것이 아니라 **하자가 많으면 정밀도가 저절로
오르기 때문**이다. 한쪽만 인용하면 그 차이가 실력으로 읽힌다.

**최고 성능은 어느 조건에서든 룰엔진 단독이다.** 모델을 얹으면 F1 이 균형 조건에서
**0.0102**, 실제 비율 조건에서 **0.0020** 내려간다.

**Critical 오탐률은 두 조건 모두 0.00%** 다(20번 · v2 5.3 기준 5% 이하). 다만 이
수치를 룰의 정확성으로 읽으면 안 된다 — 5.8 절의 '발화 0'과 같은 이유로, **합성
생성기가 만든 정상 서류가 깨끗하기 때문**이기도 하다. 실물 말뭉치에서 다시 재야 한다.

**v2 10.4 는 이 표만으로 성공이 아니다.** 8.1 의 임계값(0.85)은 두 구성 모두 넘지만,
10.4 가 성공 판정에 붙인 후반 조건 — *룰 단독 대비 개선* — 은 부호가 반대다. 즉
**현재 상태는 10.4 기준으로 "F1 목표 달성 · 개선 조건 미충족"으로 보고해야 한다.**
왜 그런지와 그럼에도 모델을 두는 이유는 3.1 에 있고, 이 판정 기준 변경이 발표
문구에 미치는 영향은 2.2 에 적었다.

이 부호가 바뀐 것은 12번(missing_field 재현율)을 처리하면서다. 경과는 이렇다.

| 시점 | 룰만 | 룰+모델 | 모델 기여 |
|---|---|---|---|
| D018 수정 전 | 0.8808 | 0.9115 | **+0.0307** |
| D018 수정 후 | 0.9042 | 0.9105 | **+0.0063** |
| 12번 이후 | 0.9210 | 0.9123 | **−0.0087** |
| **개발셋 분리 후 (현재)** | **0.9124** | 0.9022 | **−0.0102** |

> 마지막 줄은 **측정 방식이 바뀐 값**이라 위 세 줄과 같은 축이 아니다. 앞의 셋은
> 룰을 고치며 본 서류로 잰 값이고, 마지막은 처음 보는 서류로 잰 값이다(16번).

**룰이 정확해질수록 모델의 기여가 줄어들다가, 끝내 음수가 됐다.** 우연이 아니라 3.1 절이 예측한 대로다. 자세한 해석과 대응은 3.1 을 볼 것.

10,000건으로 늘려도 F1 은 거의 오르지 않는다. 성능 한계가 데이터 양이 아니라 특징 설계에 있다는 신호이며, 이 역시 3.1 과 같은 이야기다.

### 2.1 PaddleOCR 실동작 검증 결과 (4번 완료 · 13번 발생)

`aiService/.venv` (Python 3.12.10, Windows 10) 에서 확인했다.

| 확인 | 결과 |
|---|---|
| 휠 | `paddlepaddle-3.3.1-cp312-cp312-win_amd64.whl` — **붙는다** |
| 설치 | `requirements.txt` 전량 성공. paddleocr 3.7.0 / paddlex 3.7.2 |
| `paddle.utils.run_check()` | 통과 |
| 모델 | PP-OCRv6_medium det·rec + textline_ori, `~/.paddlex` 캐시 |
| 인식 | 합성 B/L 19개 박스, OCR 평균 신뢰도 0.993 |

**oneDNN 크래시.** 설치만으로는 안 됐다. 텍스트 검출 추론이 항상 죽었다.

```
NotImplementedError: (Unimplemented) ConvertPirAttribute2RuntimeAttribute
not support [pir::ArrayAttribute<pir::DoubleAttribute>]
(at onednn_instruction.cc:118)
```

PIR 실행기가 oneDNN 커널의 double 배열 속성을 변환하지 못하는 문제로 입력과
무관하게 재현된다. `enable_mkldnn=False` 로 통과한다 (`ocr/extractor.py`
`_ENABLE_MKLDNN`).

**그 대가가 13번이다.** oneDNN 은 CPU 추론 가속이므로, 끄면 느려진다.

```
init(모델 로드)   10.8s   ← 1회
warm 추론         76.5s / 77.1s / 83.8s
```

모델 로드가 아니라 **매 요청마다** 드는 비용이다. 업로드 후 80초를 기다리는
시연은 성립하지 않는다.

**해결 — 검출·인식 모델 교체 (13번 완료).** 구성별로 재봤다.

| 구성 | 추론 | 핵심값 | 평균 신뢰도 |
|---|---|---|---|
| `v6_medium` (PaddleOCR 기본) | 88.0s | 8/8 | 0.995 |
| `v6_small` | 14.0s | 8/8 | 0.995 |
| `v6_tiny` | 6.0s | 8/8 | 0.982 |
| `v5_mobile` | 13.1s | 8/8 | 0.983 |
| **`v6_small` + textline off** | **10.6s** | **8/8** | **0.995** ← 채택 |

`small` 은 `medium` 과 평균 신뢰도가 같으면서 8배 빠르다. `tiny` 가 더 빠르지만
신뢰도가 떨어져 실물 스캔에서 먼저 무너질 쪽이다. 파이프라인 실측(전처리·파싱
포함)은 **12.6~14.7초**.

**이 표를 정확도 근거로 읽지 말 것.** 입력이 합성 B/L 1장, 그것도 깨끗하게
렌더링된 텍스트라 여섯 구성이 전부 8/8 을 맞췄다. 즉 이 측정은 **속도만
구분했고 정확도는 구분하지 못했다.** `small` 이 실물 스캔에서 `medium` 만큼
읽는지는 아직 모른다. 실물 샘플이 생기면 `ocr/extractor.py` 의
`_TEXT_DET_MODEL` 부터 재검증할 것.

**아직 검증되지 않은 것 — 필드 매핑.** 위 확인은 *OCR 이 글자를 읽는가* 까지다.
읽은 글자가 올바른 필드에 꽂히는지는 확인하지 못했다. 합성 B/L 로 돌리면 값이
밀린다(`선적항` = "DATE OF ISSUE"). `field_parser` 의 구역 좌표가 라벨 데이터셋
해상도(1654×2340) 기준으로 교정돼 있어 임의 레이아웃에서 어긋나는 것으로 보이며,
라벨 JSON 경로 테스트가 전부 통과하는 것이 그 근거다. 즉 **아래 2번(실제 샘플
서류)이 F1 뿐 아니라 이 경로의 전제이기도 하다.**

### 압축되지 않는 세 가지

추정을 낙관적으로 만들면 안 되는 지점이다.

**1. OCR 정확도 — 실물 스캔에서.** 이전 판은 "Windows 에 `paddlepaddle` 휠이 붙지 않을 위험"을 최대 불확실성으로 꼽았다. **틀렸다. 휠은 붙는다.** 그 다음 판은 추론 속도(88초)를 꼽았다. **그것도 모델 교체로 풀렸다**(13초, 2.1절).

두 번 연속 빗나간 이유는 같다. **측정하기 쉬운 것을 리스크로 골랐다.** 설치 여부와 실행 시간은 명령 한 줄로 확인되므로 결론이 빨리 나고, 그래서 빨리 지워진다.

남은 불확실성은 측정이 어려운 쪽이다. **`v6_small` 이 실물 B/L 스캔을 읽는지 모른다.** 지금 근거는 합성 이미지 1장뿐이고, 거기서는 여섯 구성이 전부 만점이라 아무것도 구분되지 않았다(2.1절). 필드 매핑도 같은 이유로 미검증이다. 이건 아래 2번이 해결되기 전에는 확인할 방법이 없으며, 확인되지 않은 채로 발표에 들어가는 것이 지금 가장 큰 위험이다.

**2. 실제 샘플 서류.** 6·7번은 Invoice·Packing List 실물이 있어야 필드 좌표와 파싱 규칙을 맞출 수 있다. 합성 데이터만으로 맞추면 실물에서 깨진다. 코드 작업이 아니므로 도구로 줄지 않는다.

**3. 조문 인용의 정확성.** 룰 카탈로그의 `source`(예: `UCP 600 Art.14(c)`)가 실제 조문과 맞는지는 무역 실무 지식이 필요하다. 기획안 9절도 대응책으로 "멘토 기업 실무 검증"을 명시한다. 발표에서 조문이 틀리면 시스템 전체의 신뢰가 무너지므로, 코드 완성과 별개로 검증 일정을 잡아야 한다. **v2 10.5 가 이 방향을 규범으로 못박았다** — 조문·표준에서 유래한 값(UCP600 21일·±5%·±10%, ISO 6346, UN/LOCODE)은 임의 조정 대상이 아니며 근거 규정 개정이 있을 때만 바꾼다.

**5. 명세 수치의 지위가 규정됐다 (10.5).** 5장의 임계값·규모·성능 목표는 "실측이나 실무 검토로 확정된 값이 아닌 초기 목표치"이며, **조정할 때 5장과 10장을 함께 갱신하고 근거를 남기라**고 못박는다. 우리가 8번에서 "표는 ISBP 2건이라 적었지만 실제는 5건이었다"로 겪은 종류의 어긋남을 문서 규범으로 막는 조항이다. 앞으로 수치를 움직일 때는 이 문서에 이유를 남기는 것으로 끝내지 말고 **기획안 쪽 갱신도 요청할 것.**

## 3. 알려진 결함

### 3.1 XGBoost 가 룰엔진을 되학습한다 — 그리고 이제 손해다

**이 절이 이 문서에서 가장 중요하다.** 모델의 기여가 음수가 됐다.

특징 중요도 상위 2개가 모두 룰엔진 출력이며, 전체의 **87.7%** 를 차지한다(5개 시드 평균, 개발셋 분리 후).

| 특징 | 비중 | 성격 |
|---|---|---|
| `critical_count` | 80.9% | 룰엔진 출력 |
| `violation_weight_sum` | 6.8% | 룰엔진 출력 |
| `mean_confidence` | 1.5% | 원시 특징 (룰이 못 보는 정보) |
| `anchor_derived_ratio` | 1.5% | 원시 특징 (룰이 못 보는 정보) |
| `days_to_expiry` | 1.5% | 원시 특징 |
| `low_confidence_ratio` | 1.5% | 원시 특징 (룰이 못 보는 정보) |
| `days_to_shipment_deadline` | 1.5% | 원시 특징 |
| `evaluated_count` | 1.4% | 룰엔진 출력 |

모델이 하는 일은 새 지식의 학습이 아니라 **룰 결과의 재가중**이다. 그리고 룰이 정확해지면 재가중은 개선이 아니라 훼손이 된다.

| 시점 | 룰만 | 룰+모델 | 모델 기여 |
|---|---|---|---|
| D018 수정 전 | 0.8808 | 0.9115 | +0.0307 |
| D018 수정 후 | 0.9042 | 0.9105 | +0.0063 |
| 12번 이후 | 0.9210 | 0.9123 | −0.0087 |
| **개발셋 분리 후 (현재)** | **0.9124** | 0.9022 | **−0.0102** |

**네 번 연속 같은 방향이다.** 룰 보강(8번 ISBP)을 더 하면 더 내려간다고 보는 것이 맞다.

마지막 줄은 **측정 방식이 바뀐 값**이다(16번). 처음 보는 서류로 재자 룰 단독이
0.9210 → 0.9124 로 내려갔는데, 그 하락분이 곧 **룰을 고치며 본 서류를 평가에 다시
써서 얻고 있던 값**이다. 크지 않다는 것이 이 수치의 좋은 소식이고 — 룰이 특정 서류에
맞춰진 정도가 작다는 뜻이다 — 그럼에도 **모델 기여는 더 내려갔다**(−0.0087 → −0.0102).

> **8번을 한 뒤에도 내려가지 않았다** (−0.0073 → −0.0059). 예측이 빗나간 것이
> 아니라 **예측의 전제가 성립하지 않았다** — 신규 5건이 평가셋에서 한 번도
> 발화하지 않아 룰이 실제로 세지지 않았기 때문이다. 5.8 절에 근거를 적었다.

OCR 신뢰도 계열(`mean_confidence`, `low_confidence_ratio`, `anchor_derived_ratio`)이 룰엔진이 볼 수 없는 유일한 독립 신호인데 합계 4.5% 만 쓰인다. 모델의 존재 이유가 여기 있는데 데이터가 그 신호를 만들어 주지 않는다.

**3열 비교군 (10번 — 완료).** `python -m mlModel.evaluate` 가 매번 출력한다. 5개 시드 평균, 균형 50% 조건, 개발셋 분리 후다.

| 구성 | 정밀도 | 재현율 | F1 |
|---|---|---|---|
| **룰엔진만** | 0.9685 | 0.8625 | **0.9124** |
| **원시 특징만** (룰 출력 제외) | 0.5846 | 0.6368 | **0.6091** |
| 룰 + XGBoost | 0.9413 | 0.8667 | 0.9022 |

읽는 법은 이렇다. **모델은 룰과 독립적으로도 F1 0.61 을 낸다** — 무작위(≈0.5)보다 낫고, 룰이 없어도 서류 상태만으로 하자를 어느 정도 가린다는 뜻이다. 그러나 룰 단독의 67% 수준이고, 결합하면 오히려 −0.0102 이다. 즉 **모델이 아는 것을 룰이 전부 알고 있고, 모르는 것을 모델이 덧붙이면 틀린다.**

#### 발표에서 어떻게 말할 것인가

숨기지 않는 쪽을 택했다. 표를 감추면 "룰+모델" 수치를 방어해야 하는데, 그 수치가 룰만보다 낮다는 것은 질문 하나로 드러난다.

할 말은 셋이다.

1. **현 최고 성능은 룰엔진 단독 F1 0.9124 이며 기획안 8.1 목표(0.85)를 넘는다.** 목표 달성 여부는 모델과 무관하게 성립한다.
2. **모델의 기여가 음수인 이유는 데이터에 있다.** 합성 라벨이 룰과 같은 규칙에서 나왔으므로 모델이 배울 수 있는 것은 룰의 재가중뿐이고, 룰이 정확해질수록 재가중할 여지가 사라진다. 실제로 룰을 고칠 때마다 기여가 +0.0307 → +0.0063 → −0.0087 → −0.0102 로 단조 감소했다.
3. **모델이 기여할 자리는 남아 있다** — OCR 신뢰도 계열은 룰이 원리적으로 볼 수 없는 신호다. 다만 합성 데이터는 "OCR 이 흐릿하게 읽은 서류가 실제로 반려되더라"를 만들어내지 못한다. 기획안 3.1 ④ 피드백 플라이휠이 **실전 라벨**을 쌓아야 이 축이 열린다.

즉 이 표의 주장은 "모델이 쓸모없다"가 아니라 **"합성 데이터로는 모델의 값어치를 증명할 수 없다"** 이다. 그것이 실전 라벨 수집이 로드맵에 있는 이유다.

> **대안을 검토했고 채택하지 않았다.** 모델을 파이프라인에서 빼면 F1 이 0.9022 → 0.9124 로 오른다. 그럼에도 두지 않기로 한 이유는 위 3번이다 — 축을 지금 걷어내면 실전 라벨이 쌓였을 때 다시 세워야 한다. 다만 **F3 응답의 헤드라인 수치로는 룰엔진 단독 값을 쓴다.** 낮은 쪽을 대표값으로 내보낼 이유가 없다.

#### 그래서 모델을 어디에 쓰는가 (5.6절에서 구현)

"두되 헤드라인은 룰" 까지는 위에서 정했다. 남은 질문은 **모델이 실제로 무엇을 맡느냐** 였고, 두 가지를 더 재서 답했다.

**1. 임계값을 옮기면 되는 문제가 아니다.** 0.5 가 최적이 아닐 수 있으니 0.20~0.80 을 전부 훑었다.

| 임계값 | 룰+모델 F1 | 룰 단독 대비 |
|---|---|---|
| 0.50 (기본) | 0.9108 | −0.0101 |
| **0.75 (최적)** | **0.9158** | **−0.0052** |

최적으로 옮겨도 진다. **이진 판정에서 모델이 룰을 이기는 임계값은 없다.**

**2. 그런데 순위 품질은 모델이 이긴다.** F1 은 "하자냐 아니냐" 하나만 잰다. 위험도 정렬 품질(AUC)로 다시 쟀다.

| 산출 | AUC |
|---|---|
| 룰 가중치 합산 | 0.9285 |
| **XGBoost** | **0.9315** (+0.0030) |

부호가 반대다. 이유는 룰 확률의 분포를 보면 분명하다.

| | 위반 0건 서류 (302건) | 위반 있는 서류 (298건) |
|---|---|---|
| 룰 가중치 | **전건 정확히 0.000** | 중앙 0.375 |
| XGBoost | 중앙 0.126 (0.016~0.584) | 중앙 0.993 |

**룰 확률은 위반이 없으면 항상 0.000 이다** — 그 구간에서 정보량이 0 이고, 따라서 정렬이 불가능하다. 모델은 같은 구간을 0.016~0.584 로 벌린다. 그 차이가 곧 "룰은 통과했지만 서류가 부실하다"는 신호이며, 3.1 이 줄곧 말한 *룰이 원리적으로 볼 수 없는 축* 이 실제로 나타나는 유일한 자리다.

실물 응답에서도 재현된다. 같은 정상 서류인데 항차·용적 두 필드를 비우면 룰은 그대로 0.000, 모델은 0.188 → 0.391 로 오른다.

**결론 — 판정은 룰, 순위는 모델.**

| 역할 | 담당 | 근거 |
|---|---|---|
| 하자 판정 (하자냐 아니냐) | **룰엔진** | 모든 임계값에서 F1 우세. 조문을 인용할 수 있다 |
| 위험 점수 · 우선순위 | **XGBoost** | AUC 우세. 룰이 침묵하는 구간을 유일하게 구분한다 |

이 분담은 `predictor.py` 도입부가 원래 적어 둔 것과 같다 — "룰이 '이 조문에 걸린다'를 말한다면 이쪽은 '은행이 하자로 잡을 것 같다'를 말한다". 지금까지 그 문장이 코드로는 지켜지지 않았을 뿐이다(모델이 아예 연결돼 있지 않았다).

### 3.2 `missing_field` 재현율 — 해결됨 (0.8155 → 1.0000)

`stale_presentation` 은 5절에서 해결했다. 이제 유일하게 1.0 이 아닌 유형이다.

**해결됐다(12번).** 이제 10개 유형 전부 재현율 1.0000 이다. 남기는 이유는 원인이 두 가지였고 **성격이 서로 달랐기** 때문이다.

| 누락 필드 | 처리 전 검출/미검출 | 원인 |
|---|---|---|
| `bl_no` · `consignee` | 정상 | — |
| `vessel` | 2 / **9** | 룰의 구멍 |
| `notify_party` | 0 / **68** | **라벨의 오류** |

**선박명 — 룰의 구멍.** D011 의 severity 가 `warning` 이었다. 판정 기준이 `has_critical` 이므로 warning 은 검출로 세어지지 않고, 그래서 통째로 빠져나갔다. `critical` 로 올렸다. 근거는 카탈로그 일관성이 아니라 조문이다 — Art.20(a)(ii) 는 본선적재를 **지정 선박**에의 적재로 표시할 것을 요구하므로, 선박명이 없으면 선적 사실 자체가 표시되지 않은 것이다.

**통지처 — 라벨의 오류.** 이쪽은 룰이 아니라 **합성 생성기가 틀렸다.** 통지처 누락을 무조건 하자로 라벨링했는데, 실무에서 통지처는 L/C 가 지정한 경우에만 하자다.

이 구분이 중요하다. **틀린 라벨에 룰을 맞추면 재현율은 오르지만 정상 서류를 하자로 잡게 된다.** 즉 재현율을 올리려는 시도가 정밀도를 무너뜨린다. 지표를 맞추려다 시스템을 망가뜨리는 전형적인 경로다.

그래서 라벨 쪽을 고쳤다.

- `LCTerms.notify_party` — L/C 의 통지처 지정 여부. **비어 있는 것과 지정된 것은 의미가 다르다.**
- `checks.required_if_lc` — 지정이 있을 때만 필수. 지정이 없으면 `passed` 가 아니라 `not_evaluated` 다. 검사해서 통과한 것과 검사 대상이 아니었던 것은 다르고, 그 차이가 리포트에 드러나야 한다.
- 합성 생성기 — L/C 가 60% 확률로 통지처를 지정한다. 전건에 지정을 넣으면 조건부 룰을 만들어 놓고 조건이 항상 참인 데이터로 재는 셈이다.
- D010 을 `required_if_lc` / `critical` 로. 조건이 붙었으므로 올릴 수 있다. 이전에는 조건 없이 전건에 걸리는 룰이라 warning 이 아니면 정상 서류를 하자로 만들었다.

**부작용은 3.1 에 적었다.** 룰만 F1 이 0.9042 → 0.9210 으로 올랐지만, 같은 이유로 모델 기여가 +0.0063 → −0.0087 로 부호가 바뀌었다.

### 3.3 텍스트 레이어 PDF 는 사람에게 아무것도 묻지 않는다

**실패 방향이 나쁜 결함이다.** 조용히 틀린 답을 확신을 담아 내놓는다.

임의 레이아웃 PDF 로 돌리면 값이 밀린다. 라벨 텍스트가 값으로 잡히는 식이다.

| 필드 | 추출값 | 실제 |
|---|---|---|
| `vessel` | `OCEAN` | MSC BIANCA |
| `voyage_no` | `VESSEL` | V.112 |
| `description_of_goods` | `DESCRIPTION OF GOODS GROSS WEIGHT / SAW MACHINE FOB` | SAW MACHINE FOB |
| `place_of_issue` | `PLACE OF ISSUE PUSAN DATE OF ISSUE` | PUSAN |

밀리는 것 자체는 2.1 절이 이미 지적한 필드 매핑 문제다(구역 좌표가 라벨 데이터셋 레이아웃 기준). **새로운 문제는 그 다음이다.**

```
source=pdf-text | 검증가능=True | 확인필요 0개
   vessel      OCEAN     conf=1.00
   voyage_no   VESSEL    conf=1.00
```

**전 필드가 신뢰도 1.00 이고 확인 대기열이 비어 있다.** 텍스트 레이어는 글자를 정확히 읽은 것이 맞으므로 1.0 이 틀린 값은 아니다. 그러나 S3 편집기의 확인 유도는 신뢰도로 도는데, *글자를 정확히 읽었는가* 와 *올바른 필드에 꽂혔는가* 는 다른 질문이다. PDF 경로는 전자만 답하면서 후자까지 답한 것처럼 보인다.

이미지 경로에는 이 문제가 없다 — OCR 신뢰도가 자연히 흔들려 낮은 값이 확인 큐에 뜬다. **정확한 입력일수록 검토가 사라지는 역설**이 PDF 경로 고유의 함정이다.

**대응 후보** (아직 착수하지 않음):

1. 구역 판정으로 잡힌 값과 앵커로 잡힌 값에 서로 다른 신뢰도를 주기 — `RegionContent.confidence_factor` 가 앵커 쪽에 이미 하는 일을 구역 쪽으로 넓힌다
2. 값에 필드 라벨 문자열이 그대로 섞였으면(`DESCRIPTION OF GOODS` 등) 감점 — 위 4건 중 3건이 이 신호로 잡힌다
3. `source == "pdf-text"` 일 때 핵심 필드를 무조건 확인 대기열에 넣기 — 가장 단순하고, 시연에서 "사람이 확인한다"를 보이기에도 맞다

6번(서류 세트 확장)·2번(실제 샘플 서류)이 선행되어야 근본 해결이 된다. 그 전까지는 3번 후보가 안전한 임시 조치다.

## 5. 이번 세션에서 수정한 결함

회귀 방지를 위해 남긴다. 셋 다 **실패 방향이 나빴다** — 조용히 틀린 답을 내놓는 유형이다.

| 결함 | 증상 | 수정 |
|---|---|---|
| 앵커 추출 신뢰도 감점 누락 | 좌표가 아닌 라벨 근접으로 찾은 값이 만점 신뢰도를 받아, S3 편집기의 확인 유도가 작동하지 않음 | `RegionContent.confidence_factor` |
| `dict` / `BLFields` 접근자 불일치 | `getattr` 만 사용해, `dict` 입력 시 전 필드가 `None` → **정상 서류에 치명 하자 4건 날조**, L/C 대조 룰 14건은 평가불가 | `checks.field_value()` + `RuleEngine.verify()` 입력 형 검증 |
| 리포트 출처 거짓 표기 | LLM 실패로 템플릿이 쓰였는데 PDF 각주에 "AI 생성 요약" 표기 | `Summary` 데이터클래스로 출처를 반환값에 포함 |

두 번째 결함은 입력 형 오류가 룰별 예외 처리에 흡수되어 카탈로그 전건이 `skipped` 가 되는 경로도 함께 막았다. 그 상태는 위반 0건이라 **"하자 없음"으로 읽힌다.** 호출부의 형 오류는 검증 결과가 아니라 예외로 알려야 한다.

### 5.1 `stale_presentation` 재현율 0.4894 (9번)

재현율 0.4894 는 **검출 실패가 아니라 두 개의 별개 결함**이었다. 47건 중 D018 은 실제로 44건(0.9362)에서 발화하고 있었고, 단독 주입 시에는 22/22 전부 잡았다.

| # | 결함 | 증상 | 수정 |
|---|---|---|---|
| 1 | D018 severity 가 `warning` | 유형별 재현율은 `has_critical` 로 잰다. WARNING 룰은 아무리 정확해도 이 지표에서 영원히 미검출로 집계된다. 0.4894 는 "함께 주입된 다른 하자가 CRITICAL 일 확률"이었다 | `rules.yaml` D018 → `critical`, weight 0.30 |
| 2 | 합성 생성기의 하자 충돌 | `late_shipment` 와 `stale_presentation` 이 둘 다 `on_board_date` 를 쓴다. 함께 주입되면 나중 것이 앞의 것을 덮어쓰는데 `injected` 에는 둘 다 남아, **서류에 없는 하자를 라벨이 주장했다** (47건 중 3건) | `synth.CONFLICTING_KINDS` + `_drop_conflicts()` |

두 번째가 더 나쁜 유형이다. 라벨이 서류와 어긋나면 그 뒤로 재는 모든 수치가 검출기가 아니라 **생성기의 결함**을 측정한다.

D018 을 CRITICAL 로 올린 근거는 UCP 600 Art.14(c) 다. 제시기간 경과(stale B/L)는 은행이 수리를 거절하는 하자이지 경고가 아니다. 기존 룰 제목 "서류제시기간 임박·경과"도 부정확했다 — `presentation_period` 체크에는 임박 분기가 없고 경과만 판정하므로 "경과"로 고쳤다.

**결과:** `stale_presentation` 재현율 0.4894 → **1.0000** (5개 시드 전부). 회귀 테스트 3건 추가 (`test_rule_engine.py` 1 · `test_defect_model.py` 2).

**부작용:** 룰이 세지면서 1절·3.1 의 수치가 모두 이동했다. 룰 단독 F1 0.8808 → 0.9042, 모델 기여 +0.0307 → +0.0063. 발표 자료에 옛 수치가 남아 있으면 갱신할 것.

### 5.2 순환논리 대응 비교군 (10번)

3.1 의 질문 — "모델이 룰을 되학습한 것 아닌가" — 에 답하려면 룰 없이 어디까지 가는지를 재는 축이 필요했다. 특징 그룹을 코드에 박고, 평가 하네스에 세 번째 축을 추가했다.

| 추가 | 위치 | 역할 |
|---|---|---|
| `RULE_DERIVED_FEATURES` · `RAW_FEATURE_NAMES` | `features.py` | 룰 출력 6개 / 원시 8개의 경계를 데이터로 선언 |
| `select()` | `features.py` | 전체 행에서 이름으로 열을 뽑는다 |
| `DefectPredictor(feature_names=...)` | `predictor.py` | 부분집합 모델. 열을 고르는 일은 **예측기가** 한다 |
| `EvaluationReport.raw_features_only` | `evaluate.py` | 세 번째 축 + 3열 비교표 렌더링 |

설계에서 두 가지를 의도적으로 정했다.

**1. 부분집합 모델도 전체 피처 행을 받는다.** 호출부가 자르게 두면 학습과 추론에서 서로 다르게 자를 수 있고, 그 오류는 예외 없이 조용히 틀린 확률로 나온다. 잘라 넣은 행은 열 수 검사에서 `ValueError` 로 막는다.

**2. 비교군은 `best_f1` 에 넣지 않는다.** 그건 배포 후보가 아니라 진단용 축이다. 넣으면 진단 수치가 기획안 8.1 목표 달성 판정을 밀어 올릴 수 있다.

경계가 흐려지면 3열 비교의 의미가 사라지므로, `verdict` 를 비웠을 때 룰 출력 피처만 변하는지 확인하는 테스트를 두었다. 회귀 테스트 11건 추가.

**결과는 3.1 절.** 요약하면 원시 특징만으로 F1 0.60, 결합 이득 +0.012 다.

### 5.3 리포트 공유 (11번)

기획안 5절이 "PDF 출력·**공유** 가능"을 요구하지만, `api/main.py` 는 "저장하지 않는다"를 설계로 못박고 있다. 리포트를 저장하기 시작하면 만료·삭제·권한까지 AI 모듈이 떠안고, 게이트웨이와 저장 책임이 겹친다.

**그래서 링크가 입력을 싣는다.** 토큰은 `v1.<zlib+base64url(입력)>.<HMAC-SHA256>` 이고, 열릴 때마다 서버가 같은 리포트를 다시 조립한다. 저장소도 DB 도 없다. 전체 B/L + L/C 를 실어도 **620자 안팎**이다.

| 추가 | 위치 |
|---|---|
| `encode` · `decode` · `expires_at` · `share_secret` | `report/share.py` (신규) |
| `POST /report/share` | 링크 발급 |
| `GET /report/shared/{token}` · `.../pdf` | 열람 (PDF 는 `inline`) |

설계에서 정한 것들.

- **발급 시 한 번 조립해 본다.** 열어 봐야 400 이 나는 링크를 쥐여주면 공유받은 쪽에서 터지고, 그때는 원인을 알 방법이 없다
- **서명을 먼저 확인하고 그 다음에 압축을 푼다.** 반대 순서면 서명 없는 입력이 zlib 에 먼저 들어가 압축폭탄이 검사 앞에서 터진다
- **만료는 410, 서명 실패는 404.** 만료를 404 로 내면 받은 쪽이 "주소가 틀렸나"를 의심하게 된다
- **PDF 는 `inline`.** `attachment` 면 받는 쪽이 파일을 내려받아 여는 한 단계를 더 거친다

**한계 두 가지를 알고 쓸 것.**

1. **토큰은 암호문이 아니다.** 서명은 위조를 막을 뿐 내용을 가리지 않는다. 링크를 가진 사람은 base64 를 풀어 B/L 원문을 읽는다. 받을 사람은 어차피 리포트를 볼 사람이라 의도상 문제는 아니지만 **링크가 새면 서류가 샌다.** 완화책은 짧은 만료뿐이다(기본 7일)
2. **`REPORT_SHARE_SECRET` 미설정 시 프로세스마다 임시 키를 쓴다.** 재시작하면 링크가 전부 죽는다. 고정 기본값을 두면 소스를 읽은 누구나 위조할 수 있으므로 이쪽을 택했고, 기동 로그와 발급 응답(`ephemeral_secret`)이 상태를 알린다

회귀 테스트 17건 추가 (`test_api.py` 9 · `test_report.py` 8) — 왕복 동일성, 위조·본문변조 차단, 만료 410, 발급 시 검증, URL 길이 거절.

### 5.4 PDF 입력 (1번)

**텍스트 레이어가 있으면 OCR 을 아예 타지 않는다.** 전자 발행 B/L·인보이스는 대부분 텍스트 레이어를 갖는데, 그걸 이미지로 굽고 OCR 에 넣는 것은 정확한 글자를 흐린 픽셀로 바꿔 다시 추측하는 셈이다. 정확도가 떨어지고 시간도 든다.

```
소요 0.39초 · source=pdf-text · 15개 필드 전부 추출
```

같은 서류를 OCR 로 돌리면 13초다(2.1절). **33배 차이이고, PaddleOCR 이 없어도 돈다** — 1번이 시연 항목이었던 이유가 이것이다.

| 추가 | 위치 |
|---|---|
| `from_pdf` · `_pdf_text_bboxes` | `ocr/extractor.py` |
| `run_from_pdf` | `ocr/pipeline.py` |
| `POST /extract/pdf` (`page` 파라미터) | `api/main.py` |
| `write_bl_pdf` · `bl_pdf` · `scanned_pdf` 픽스처 | `tests/conftest.py` |

**기존 파서를 그대로 재사용한다.** `FieldParser.REGIONS` 가 비율(`xr`/`yr`) 기반이라 A4 595×842 든 라벨 데이터셋 1654×2340 이든 좌표계가 흡수된다. 이것이 사실인지를 테스트가 직접 잡는다 — 같은 bbox 목록으로 만든 PDF 와 라벨 JSON 이 **완전히 동일한 초안**을 내는지 비교한다. 새 파서를 만들지 않았다는 증거다.

설계에서 정한 것들.

- **줄(line) 단위로 묶는다.** 단어 단위는 라벨 JSON 보다 잘게 나뉘어 구역 안에서 값이 조각나고, 블록 단위는 여러 필드가 한 상자에 섞인다
- **텍스트 줄 10개 미만이면 스캔본으로 본다.** 스캔 PDF 에도 워터마크·도장·쪽번호 정도의 텍스트는 있다. 그걸 보고 "텍스트 레이어 있음"으로 판단하면 본문이 통째로 빠진 결과를 자신 있게 내놓는다
- **PDF 여부는 확장자가 아니라 `%PDF` 매직바이트로 판정한다.** 이미지를 `.pdf` 로 바꿔 올리는 일이 흔하고, 그때 PyMuPDF 오류를 그대로 흘리면 원인을 알 수 없는 500 이 된다
- **`source` 에 `pdf-text` / `pdf-ocr` 를 남긴다.** 신뢰도 1.0 이 '원문 그대로'인지 'OCR 이 확신한 값'인지는 전혀 다른 이야기이고, 화면이 구분할 수 있어야 한다
- **`pymupdf` 를 `fitz` 보다 먼저 import 한다.** 구 이름은 import 마다 폐기 경고를 찍는데, 매 요청 로그에 섞이면 진짜 경고가 묻힌다

회귀 테스트 13건 추가 (`test_extractor.py` 7 · `test_api.py` 6).

**남긴 결함:** 3.3 절. 이 경로는 전 필드를 신뢰도 1.0 으로 내놓아 확인 대기열이 비는데, 임의 레이아웃에서는 값이 밀린다. 14번으로 세워 두었다.

### 5.5 엑셀·이메일 입력과 LLM 구조화 추출 (2·3·5번)

세 입력을 모두 **같은 `OCRResult` 로 모아** 기존 파서를 쓴다. 입력 형식마다 매핑 경로를 두면 "B/L 번호를 어떻게 찾는가"가 네 갈래로 갈리고, 앵커 테이블을 고칠 때 네 곳을 고쳐야 한다. 하나를 빠뜨리면 특정 입력에서만 필드가 비는 버그가 된다.

**엑셀 (2번).** 셀을 좌표로 펼친다. 엑셀에는 픽셀 좌표가 없고 행·열만 있으므로 그리드를 캔버스에 펼쳐 `BBox` 로 만든다. 시트는 값이 가장 많은 것을 고른다 — 첫 시트를 쓰면 표지 시트가 앞에 있는 파일에서 빈 결과가 나온다.

**이메일 (3번).** **첨부를 먼저 본다.** 실무에서 이메일 본문은 대개 안내문이고 첨부가 서류다. 본문부터 읽으면 선하증권 대신 "Please find attached" 를 파싱한다. 우선순위는 PDF > 엑셀 > 이미지이고, 이미지가 마지막인 이유는 유일하게 추측이 들어가는 경로이기 때문이다. 어느 경로였는지는 `source` 에 남는다.

**LLM 구조화 추출 (5번).** 대체가 아니라 보충이다. 파서가 **비운 핵심 필드만** 채우고, 파서가 찾은 값은 LLM 이 더 그럴듯한 답을 내놔도 건드리지 않는다 — 설명 가능한 값을 설명 불가능한 값으로 바꾸는 거래는 남는 장사가 아니다.

기본이 꺼짐이다(`LLM_STRUCTURED_EXTRACT`). 외부 API 호출이므로 켜져 있으면 테스트와 시연이 네트워크·요금·지연에 묶이고, 그 사실이 코드 어디에도 드러나지 않는다.

#### 만들면서 드러난 기존 결함 세 가지

**1. 구역 판정이 그리드 입력에 해롭다.** 엑셀을 구역으로 읽으면 선적항 자리에 양하항과 화물명세가 통째로 들어온다. 그리고 **값이 있으므로 앵커까지 가지 않는다.** `LAYOUTLESS_SOURCES` 로 이런 입력은 구역을 건너뛴다.

**2. 앵커가 아래쪽까지 끌어온다.** B/L 서식은 라벨 아래에 값이 오는 배치가 흔하지만, 그리드에서 **아랫줄은 다른 필드**다. `same_line_only` 를 추가했다.

**3. 수하인·통지처·선박명에 앵커 대체 경로가 없었다.** 구역이 비면 무조건 `None` 이었다. 지면 배치가 없는 입력에서 이 세 필드가 항상 비는 원인이었다.

#### 초안이 값의 출처를 드러낸다

`DraftField.source` 를 추가했다(`region` / `anchor` / `llm`). 없으면 화면이 LLM 이 낸 값과 좌표로 찾은 값을 구분할 수 없다.

**신뢰도만으로는 부족하다.** 0.55 라는 숫자는 "좌표로 찾았는데 OCR 이 흐릿했다"와 "LLM 이 원문을 보고 답했다"를 구분하지 못하는데, 사람이 그 값을 확인하는 방법은 둘이 전혀 다르다. 앞은 원본 이미지의 그 자리를 보면 되고, 뒤는 서류 전체에서 근거를 찾아야 한다.

### 5.6 XGBoost 모델 학습·연결

**학습 전 상태에서 가장 중요한 사실:** `DefectPredictor` 가 **API·리포트 어디에도 연결돼 있지 않았다.** 전부 `verdict.defect_probability`(룰 가중치 합)를 쓰고 있었고, XGBoost 축은 `mlModel.evaluate` 안에서만 살아 있었다. 기획안이 F3 를 "룰엔진·XGBoost 두 축"으로 규정하는데, 실제 응답에는 한 축뿐이었다.

`mlModel/artifacts/defect_model.json` (325KB) 을 학습해 저장하고, 3.1 이 정한 역할 분담대로 연결했다.

| 추가 | 위치 |
|---|---|
| `predictor()` 싱글턴 + `_predict()` | `api/main.py` |
| `VerifyResponse.prediction` | `/verify` 응답에 확률·산출 주체 |
| `build_report(..., prediction=)` | 위험 점수만 모델 값으로 교체 |

정한 것들.

- **판정은 건드리지 않는다.** `prediction` 은 응답에 추가되는 필드이고, 하자 목록·체크리스트·기한은 전부 룰엔진 결과 그대로다
- **예측이 실패해도 검증 결과는 돌려준다.** 모델은 부가 축이라, 여기서 터져 500 을 내면 룰엔진이 정상적으로 낸 하자 목록까지 함께 잃는다. 실패 시 룰 가중치로 떨어지고 출처를 `rules-v1` 로 표기한다
- **기동 시 모델 적재 여부를 확정한다.** 첫 요청에서 알게 되면 그때는 이미 `rules-v1` 로 산출된 응답이 나간 뒤다
- **`artifacts/` 를 커밋한다.** `.gitignore` 두 곳이 막고 있었다(루트의 Hardhat 규칙, `mlModel/.gitignore`). 파일이 없으면 예외가 아니라 **값이 조용히 달라지므로**, 시연 직전에 학습을 잊으면 그대로 발표에 들어간다. `meta.json` 도 함께 — 피처 순서 대조가 그 파일 없이는 통째로 건너뛰어진다

**정상 서류의 위험 점수가 0.000 → 0.19 로 바뀐다.** 룰 확률이 위반 0건에서 항상 정확히 0.000 이었던 것이 오히려 과신이었다 — 은행 심사를 아직 거치지 않은 서류에 "위험 0"을 표기하는 셈이었다. 등급(`risk_level`)은 위반 건수로 정하므로 "낮음" 그대로다.

회귀 테스트: 산출 주체 표기가 실제와 일치하는지(리포트·검증 두 응답의 `model` 이 같아야 한다), 모델이 없을 때 `rules-v1` 로 표기하는지.

> 기존 테스트 하나가 `model == "rules-v1"` 을 단언하고 있었다. 모델 연결 **이전 상태를 굳힌** 단언이라 정상 동작이 실패로 잡혔다. 재고 싶은 것은 특정 값이 아니라 표기와 실제의 일치이므로 그렇게 고쳤다.

### 5.7 서류 세트 확장 (6번)

`form_type` 이 선하증권으로 **하드코딩**돼 있었다. 추출기 네 곳(`from_json`
제외)이 전부 `form_type="선하증권"` 을 넣고 있었고, 파서는 그것만 알았다.

상업송장·포장명세서를 더했다.

| 추가 | 위치 |
|---|---|
| `DocumentSpec` · `SPECS` · `detect()` | `ocr/doc_types.py` (신규) |
| `DocumentParser` · `DocumentFields` | `ocr/doc_parser.py` (신규) |
| `build_document_draft()` · `BLDraft.form_type` | `ocr/draft.py` |
| `IntakePipeline._form_type()` 분기 | `ocr/pipeline.py` |

**선하증권만 좌표를 쓴다.** `FieldParser.REGIONS` 는 1654×2340 라벨 데이터셋
실측으로 교정된 값인데, 송장·포장명세서에는 그런 교정 데이터가 없다. 없는
좌표를 지어내면 맞을 때보다 틀릴 때가 많고, **틀려도 값이 나오므로 조용한
오추출**이 된다. 그래서 새 종류는 앵커(항목명 근접)만 쓴다. 정확도는 낮지만
출처가 분명하고, 앵커는 이미 신뢰도를 감점해 사람 확인을 유도한다.

**본문 판별이 메타데이터를 이긴다.** 추출기가 넣은 `form_type` 을 믿으면
송장을 올려도 선하증권으로 처리되어 B/L 좌표로 파싱된다. 판별에 실패하면
(`미상`) 메타데이터로 돌아간다 — 라벨 JSON 의 값은 사람이 적은 것이라
믿을 만하다. **판별 실패 시 선하증권으로 넘겨짚지 않는다**는 것이 핵심이다.

**초안 형태는 종류와 무관하게 같다.** 필드 이름·라벨·핵심 여부만 명세에서
온다. 종류마다 다른 응답 구조를 내면 S3 편집기가 종류 수만큼 렌더러를 갖게
되고, 종류를 추가할 때마다 화면도 함께 고쳐야 한다. 테스트가 이 불변을
직접 잡는다(송장 초안과 B/L 초안의 키 집합 비교).

합성 서류로 실측한 결과 **송장 9/9 · 포장명세서 10/10** 전 필드가 정확했다.

작업 중 두 가지를 함께 고쳤다.

1. **값에 다음 항목명이 딸려왔다** — `INVOICE NO` 의 값이 `INV-2026-0417
   INVOICE DATE` 로 나왔다. 파서가 다음 항목명에서 수집을 끊도록 했다.
   초안 편집기가 `LABEL_ECHOED` 로 잡아 주긴 하지만, 확인 대기열은 사람이
   봐야 고쳐지는 비용이므로 파서가 끊을 수 있으면 끊는 것이 맞다
2. **항목명 어휘가 선하증권 전용이었다** — `INVOICE DATE` 가 어휘에 없어
   3.3 절의 검사를 그냥 통과했다. 서류 명세에서 자동으로 끌어오도록 바꿨다.
   종류가 늘 때마다 어휘를 손으로 고쳐야 한다면 같은 누락이 반복된다

회귀 테스트 17건 추가 (`tests/test_doc_types.py` 신규).

**7번의 전제가 갖춰졌다.** 서류 간 정합성 대조는 비교할 서류가 둘 이상
있어야 성립한다. 명세의 필드 선택 기준도 그것이었다 — 송장에만 있고 대조할
일이 없는 항목(결제 조건, 은행 정보)은 넣지 않았다.

### 5.8 ISBP 룰 보강 (8번)

시작하면서 센 수가 문서와 달랐다. 표는 **ISBP 2건 / 21건** 이라고 적고
있었지만 실제 카탈로그는 **5건 / 24건** 이었다. 6·7번을 하면서 룰이 늘었는데
이 표만 갱신되지 않은 것이다. 잔여 작업 산정이 실제보다 크게 잡혀 있었다.

5건을 더해 **29건 / ISBP 8건** 이 됐다(서류 간 10건 별도, 그중 ISBP 5건).

| id | 룰 | 근거 | severity |
|---|---|---|---|
| D022 | 발행일 누락 | ISBP 821 E | critical |
| D023 | 고장 문언 (무고장 선하증권 아님) | UCP 600 Art.27 | critical |
| D024 | 예정 선박 표시 | UCP 600 Art.20(a)(ii) | warning |
| D025 | 항구가 특정되지 않음 | ISBP 821 E | critical |
| D026 | 운임 지급 조건 저촉 | ISBP 821 E | warning |

#### D022 는 조용한 구멍을 막는다

**D021(발행지 누락)의 조문 근거가 발행지와 발행일을 함께 요구하는데, 룰은
발행지만 검사하고 있었다.** 발행일 누락을 잡는 룰이 카탈로그에 없었다.

빠졌다는 것보다 **빠졌을 때의 실패 방향**이 문제다. 발행일이 없으면
D008(유효기간)·D018(제시기간)·D019(선일자)가 전부 `not_evaluated` 로 빠진다.
즉 **발행일을 통째로 비우면 날짜 하자가 하나도 잡히지 않고**, 위반 0건은
화면에서 '하자 없음'으로 읽힌다. 3.3 절과 같은 유형 — 조용히 틀린 답이다.

회귀 테스트가 이 연쇄를 직접 잡는다(`test_발행일이_없으면_날짜_룰이_전부_평가불가로_빠진다`).

#### 문면상 하자는 L/C 를 보지 않는다

D023·D024·D025 는 신용장이 무엇을 말하든 서류 문면 자체가 하자인 항목이라
`contains_forbidden` 을 새로 두었다. 기존 `forbidden_when_prohibited` 는 L/C 가
금지했을 때만 켜지는 조건부 룰이라, 이 셋을 그쪽으로 만들면 **L/C 없이 돌릴 때
통째로 검사되지 않는다.**

**낱말 경계로 본다.** 기존 검사는 "PARTIAL SHIPMENT" 같은 긴 구를 찾으므로 부분
일치로 충분하지만, 고장 문언은 "WET"·"TORN" 처럼 짧다. 부분 일치로 두면
`WETSUIT` 이 고장 문언으로 잡힌다. 오탐 하나가 정상 서류를 반려시키는 룰이다.

#### 운임 조건은 한 방향만 잡는다

C·D 조건(CFR·CIF·CPT·CIP·DAP·DPU·DDP)은 매도인이 주운송비를 부담하므로 운임 후불
표시가 거래조건과 저촉된다. **반대(FOB 인데 운임 선불)는 넣지 않았다** — 매도인이
편의상 선지급한 것일 수 있고 은행이 그것으로 거절하지 않는다. 대칭이 예뻐 보인다고
넣으면 정상 건이 하자로 잡힌다. 기획안 9절의 '심각도 보수적 산정'이 이 방향이다.

작업 중 결함 하나를 함께 고쳤다. 처음엔 `_first_present`(값이 있는 첫 필드)로
짰는데, 운임란에 금액이 있으면 화물 명세를 아예 보지 않는다. 후불 표시는 운임란이
아니라 명세·비고에 찍히는 일이 많으므로 **값이 있을수록 검사가 줄어드는 역전**이
된다. 대상 필드를 전부 훑도록 고쳤다.

#### 수치는 움직이지 않았다 — 그리고 그것이 한계다

| 구성 | 정밀도 | 재현율 | F1 |
|---|---|---|---|
| 룰엔진만 (전·후 동일) | 0.9832 | 0.8825 | **0.9302** |
| 룰 + XGBoost (전) | 0.9670 | 0.8825 | 0.9228 |
| 룰 + XGBoost (후) | 0.9702 | 0.8825 | 0.9243 |

룰 단독 F1 이 **한 자리도 바뀌지 않았다.** 신규 5건이 합성 정상 서류에서 한 번도
발화하지 않았다는 뜻이고, 오탐이 0 이라는 근거다. 합성 10,000건(2,000건 × 5시드)에
직접 돌려 확인했다.

```
D022  평가됨 10000   발화 0
D023  평가됨 10000   발화 0
D024  평가됨  9813   발화 0
D025  평가됨 10000   발화 0
D026  평가됨  5973   발화 0
```

**그러나 이 표를 '새 룰이 잘 동작한다'는 근거로 읽으면 안 된다.** 발화가 0 인
이유는 룰이 정확해서가 아니라 **합성 생성기가 이 하자들을 만들지 않기 때문**이다.
`synth.py` 의 `DEFECT_KINDS` 10종에 고장 문언·예정 선박·항구 미특정·운임 조건이
없다. 즉 지금 이 5건의 재현율은 **측정된 적이 없고**, 근거는 단위 테스트 11건뿐이다.

3.1 이 예측한 "룰이 세지면 모델 기여가 더 내려간다"도 이번엔 나타나지 않았다.
같은 이유다 — 룰이 실제로 세지지 않았고, 평가셋에서 달라진 것은 `evaluated_count`·
`skipped_ratio` 뿐이다(모델 기여 −0.0073 → −0.0059, 단일 시드라 과대해석 금물).

**다음 작업은 명확하다.** `DEFECT_KINDS` 에 이 4종을 주입하면 재현율을 잴 수 있다.
다만 그렇게 하면 1·3절의 수치가 전부 이동하므로 별건으로 다뤄야 한다.

#### 모델 artifact 를 재학습했다

피처 **이름**은 그대로지만 **분포**가 바뀌었다 — 룰이 5건 늘어 `evaluated_count` 와
`skipped_ratio` 가 모든 서류에서 이동한다. `meta.json` 은 피처 **순서**만 대조하므로
이 어긋남을 잡지 못한다. 즉 재학습하지 않으면 **로드는 성공하는데 값만 조용히
낡는다.** `--save-model` 로 다시 학습해 커밋했다.

> 룰 카탈로그의 지문(예: 룰 id·weight 해시)을 `meta.json` 에 함께 저장하고 기동 시
> 대조하면 이 부류를 자동으로 잡을 수 있다. 착수하지 않았다 — 불일치 시 적재를
> 거부할지 경고만 할지는 시연 안정성과 맞바꾸는 판단이라 따로 정해야 한다.

### 5.9 실물 선하증권 말뭉치

**합성 생성기가 지어내던 B/L 을 실물로 갈아끼웠다.** AI Hub 「대규모 OCR 데이터셋(물류)」
선하증권 라벨 4,000건이다. 기존 라벨 데이터셋과 같은 출처이며 — 첫 문서의 송하인이
`GAE WOON CO., LTD.`, 즉 `synth.py` 의 `COMPANIES` 와 테스트 픽스처에 그대로 박혀
있는 이름이다 — `REGIONS` 가 이 데이터에서 교정됐다는 것이 추측이 아니라 확인됐다.

#### 무엇이 실물이 되고 무엇이 아닌가

이 표를 흐리면 발표에서 과장이 된다.

| 항목 | 실물인가 |
|---|---|
| 필드 값·결측 패턴 | **예** |
| 값의 지저분함 (항목명 혼입 등) | **예** |
| 구역/앵커 판정 비율 | **예** |
| OCR 신뢰도 | **아니오** — 라벨은 정답이라 1.0 고정 |
| L/C 조건 | **아니오** — B/L 에서 역산한 합성 |
| **하자 라벨** | **아니오** — 합성 주입 |

**바뀌는 것은 서류이지 정답이 아니다.** "은행이 반려했다"는 사실은 어떤 공개
데이터에도 없다.

실측 결측률이 합성이 못 만드는 부분이다 — `voyage_no` 41.8%, `total_freight`
58.3%, `measurement` 88.0% 만 채워져 있다.

#### 세 가지가 걸렸다

**1. 실물 날짜는 서류 안에서도 안 맞는다.** 2002~2017 년에 흩어져 있고, 발행일
2006-09-06 에 선적일 2013-06-11 같은 건이 흔하다. 원본 서식의 날짜가 채워 넣은
값이지 실제 거래 기록이 아니기 때문이다. 그대로 쓰면 **300건 전건이 D018(제시기간
경과)에 걸린다.**

값을 기준 시각 근처로 옮기되 **표기 형식은 보존한다.** `SEP 06, 2006`·`16-AUG-2009`·
`09-11-2015` 같은 형식 다양성이야말로 합성이 못 만드는 실물의 성질이고,
`parse_date` 의 형식 목록을 실제로 시험하는 것도 이쪽이다.

**2. L/C 명세를 낱말로 이어붙이면 안 된다.** `MEN'S 100% COTTON` 에서 낱말만 뽑아
`MEN COTTON` 을 만들었더니 그 문자열이 원문에 없어, **서류가 자기 명세와 불일치하는
L/C** 가 만들어졌다. 300건 중 105건이 D006 에 걸렸다. 원문에 그대로 있는 연속
구간만 잘라 쓴다.

**3. 기준 서류의 '하자 없음'은 룰엔진이 판정한다.** 키워드 목록을 복제하면 룰이
늘 때마다(오늘 5건이 늘었다) 두 곳을 고쳐야 하고, 한쪽을 잊으면 기준 서류에 하자가
섞인다. 실물 3,660건 중 재추첨률은 **약 4%** 다.

#### 신뢰도를 다시 뽑는다 — 그리고 그 이유가 이 절에서 가장 중요하다

처음엔 라벨의 신뢰도(전 필드 1.0)를 그대로 썼다. 결과가 이렇게 나왔다.

| 구성 | 합성 B/L | 실물 B/L (신뢰도 1.0 그대로) |
|---|---|---|
| 룰엔진만 | 0.9302 | **0.9730** |
| 룰 + XGBoost | 0.9243 | **0.9764** |
| 모델 기여 | −0.0059 | **+0.0035** |

**모델 기여의 부호가 뒤집혔다.** 그러나 이것은 성과가 아니라 **평가셋이 쉬워진
것**이다.

`_apply_label_noise` 의 "룰이 못 잡는 하자" 채널은 **낮은 신뢰도에서 나온다.**
신뢰도 분산이 0 이면 그 잡음이 발생하지 않고, 라벨이 룰의 결정론적 함수에
가까워진다. 룰이 놓칠 수 있는 케이스가 데이터에서 사라졌으니 재현율이 오르는
것이 당연하다 (0.8825 → 0.9829).

**이 수치를 성과로 보고했다면 발표에서 거짓이 된다.** 그래서 `confidence_is_real`
을 두고, 라벨 유래 신뢰도는 생성기가 다시 뽑는다. 판정 경로(구역/앵커)는 실물
그대로 두고 앵커 감점도 추출기와 같게 준다 — 신뢰도만 무작위로 뽑으면
`anchor_derived_ratio` 와 `mean_confidence` 의 상관이 실물과 달라진다.

#### 바로잡은 뒤의 결과

| 구성 | 합성 B/L | **실물 B/L** |
|---|---|---|
| 룰엔진만 | 0.9302 | **0.9346** |
| 원시 특징만 | 0.5618 | **0.5820** |
| 룰 + XGBoost | 0.9243 | **0.9271** |
| 모델 기여 | −0.0059 | **−0.0076** |

**실물 서류를 넣어도 모델 기여는 여전히 음수다.** 3.1 의 결론이 실물에서도 그대로
성립한다 — 부족한 것은 **서류가 아니라 라벨**이기 때문이다. 서류를 4,000건 실물로
바꿔도 "은행이 하자로 잡았다"는 정답은 한 건도 생기지 않는다.

유형별 재현율도 더 이상 전부 1.000 이 아니다(`consignee_mismatch` 0.966,
`freight_deviation` 0.976). 실물이 더 어렵고, 그쪽이 정직한 값이다.

#### 데이터는 커밋하지 않는다

용량(4,000건 116MB)과 이용조건 때문이다. **말뭉치가 없으면 생성기는 기존 합성
경로로 조용히 돌아간다** — 데이터가 있는 환경에서만 좋아지고 CI 는 그대로 통과한다.
테스트는 말뭉치를 직접 만들어 검사한다(22건). 실제 데이터가 있어야만 도는 테스트를
쓰면 이 경로가 CI 에서 통째로 검사되지 않는다.

```bash
python -m mlModel.evaluate --count 2000 --corpus <라벨 디렉토리 또는 캐시 JSON>
```

#### 다음

신뢰도까지 실물로 만들려면 원천 이미지를 PaddleOCR 로 돌려야 한다. 장당 13초,
4,000장이면 14시간이다. 수백 장 규모면 현실적이고, 그 경로는 같은 `BLRecord`
형식으로 끼울 수 있게 열어 두었다(`records_from_drafts`).

### 5.10 MT700 원문 파서 (15번)

**지금까지 L/C 는 사람이 손으로 JSON 에 옮겨야 검증이 돌았다.** `LCTerms.from_tags`
는 이미 잘린 태그 dict 를 받는데, 실무에서 오는 것은 SWIFT 전문 원문이다. 그 사이가
비어 있었고, v2 10.1 이 이 경로를 이번 기간 필수 3종에 넣으면서 갭이 드러났다.

| 추가 | 위치 |
|---|---|
| `parse_mt700` · `MT700Parse` · `MT700ParseError` | `ruleEngine/mt700.py` (신규) |
| `POST /lc/mt700` | `api/main.py` |

**엔드포인트를 `/extract/*` 에 두지 않았다.** 추출 다섯 경로가 성립하는 이유는
응답 형태가 전부 같다는 데 있는데(`api.md`), 여섯 번째로 L/C 조건을 내는 경로를
끼우면 그 불변이 깨진다. 구현도 `ocr/` 가 아니라 `ruleEngine/` 이다 — 산출물이
`LCTerms` 이고 그걸 소유한 쪽이 룰엔진이다.

#### 이 파서의 실패는 조용하다

**L/C 조건이 비면 그 조건을 쓰는 룰은 `not_evaluated` 로 빠지고, 위반 0건은 화면에서
'하자 없음'으로 읽힌다.** 즉 파싱이 실패할수록 시스템이 안전해 보인다. 3.3·5.8 절이
반복해서 만난 실패 방향이 여기서도 그대로 나온다.

그래서 결과에 `lc` 만 담지 않는다.

- `tags` — 원문에서 잘라낸 **정규화 전** 값. 결과가 이상할 때 대조할 자리가 필요하다
- `unmapped` — 태그로 인식했으나 `LCTerms` 에 자리가 없는 것. 47A 가 대표적이다
- `notes` — 정규화하며 버렸거나 해석하지 못한 것

태그를 하나도 못 찾으면 **빈 `LCTerms` 대신 400 을 낸다.** 200 으로 흘리면 그 응답으로
검증이 돌고 위반 0건이 나온다.

#### 정규화에서 정한 것 넷

**1. SWIFT 의 콤마는 소수점이다.** `USD123456,78` 을 그대로 두면 `parse_amount` 가
콤마를 천단위로 보고 지워 **금액이 100배**가 된다. 송장 금액 초과(X009)가 통과해
버리는 조용한 실패라, 파서가 `USD 123,456.78` 로 표기를 확정한다.

**2. 부정형을 먼저 본다.** `NOT ALLOWED` 는 `ALLOWED` 를 품고 있다. 순서를 바꾸면
분할선적 **금지가 허용으로 뒤집혀** D013 이 통째로 잠든다. 허용/금지로 판정되지
않는 값(`CONDITIONAL` 등)은 기본값(허용)을 두고 `notes` 로 알린다 — 임의로 금지를
잡으면 정상 건이 하자가 된다.

**3. 날짜는 ISO 로 바꾼다.** 룰의 `parse_date` 는 `YYMMDD` 를 모른다. 바꾸지 않으면
날짜 룰이 위반이 아니라 '해석 실패'로 빠지는데, 화면에서 그 둘은 똑같이 '위반 없음'
으로 보인다. 세기는 2000년대로 읽는다(무역 서류에 1900년대 유효기일은 없다).

**4. 거래조건은 채우지 않는다.** MT700 에 Incoterms 전용 태그가 없어 45A 자유서식에서
뽑아야 하는데, 뽑은 값은 L/C 가 필드로 명시한 값이 아니다. `FOB` 만 담으면 송장의
`FOB BUSAN` 과 문자열이 달라 X010 이 오탐이 되고, `FOB BUSAN` 을 담으면
`FOB BUSAN, KOREA` 와 어긋난다. **어느 쪽이든 정상 서류를 하자로 만든다.** 대신
"45A 에 FOB 표기가 있다"는 사실만 `notes` 로 알리고 사람이 지정하게 했다. 기획안
9절의 '심각도 보수적 산정'이 이 방향이고, v2 5.1 의 '추정 생성 금지'도 같은 이야기다.

#### 만들면서 드러난 기존 결함 — `from_tags` 도 정규화를 타야 한다

**같은 방으로 들어가는 문이 둘인데 한쪽만 정규화하고 있었다.** `LCTerms.from_tags`
는 태그 값을 필드에 그대로 꽂았고, 그게 두 가지로 틀렸다.

| 입력 | 결과 | 왜 나쁜가 |
|---|---|---|
| `{"46A": "FULL SET OF ... B/L"}` | `documents_required` 가 **문자열** | `bl_in_documents_required` 가 문자 단위로 순회해 선하증권 요구를 못 찾는다 → **정상 L/C 에 D016(치명) 날조** |
| `{"44C": "260630"}` | 원값 그대로 | 날짜 룰이 '해석 실패'로 빠진다 → 화면에서 위반 없음과 구분되지 않는다 |

앞의 것은 5절 표의 "정상 서류에 치명 하자 4건 날조"와 같은 유형이다. `from_tags`
가 `mt700.terms_from_tags` 를 타도록 뒤를 합쳤다. `MT700_TAGS` 는 참조표로 남기되,
표에만 있고 처리기가 없는 태그가 생기지 않도록 테스트가 두 목록을 대조한다.

#### 남은 것

- **47A(추가 조건)는 판정하지 않는다.** v2 5.3 의 R-LC-47A 는 "룰이 조건 문장을
  분해하고 LLM 은 충족 여부만 판정"하는 구조인데 그 룰이 없다. `unmapped` 로 남겨
  검사하지 않았다는 사실만 드러낸다
- **`consignee` · `notify_party` 를 채우지 않는다.** MT700 에 전용 태그가 없고 46A·47A
  자유서식에 섞여 있다. 특히 통지처는 3.2 절이 다뤘듯 **지정 여부 자체가 판정을
  가르므로**(D010), 자유서식에서 추정해 채우면 없는 지정을 만들어내게 된다
- 회귀 테스트 35건 (`tests/test_mt700.py` 30 · `tests/test_api.py` 5)

### 5.11 개발셋 분리 · 비율 이중 보고 · Critical 오탐률 (16 · 17 · 20번)

셋 다 기능이 아니라 **수치의 의미를 지키는 작업**이다. 코드로 여는 것이 없어 미루기
쉬운데, 미루면 1절의 모든 숫자가 심사에서 흔들린다.

#### 16 — 개발셋과 평가셋의 서류가 겹치지 않는다

v2 10.3: "룰엔진은 정답을 보면서 만들면 성능이 자명하게 부풀려지므로, 이 분리는
성능 수치의 의미를 지키는 최소 조건이다."

**우리가 정확히 그렇게 해 왔다.** 9번(D018)·12번(missing_field)은 평가셋의 유형별
재현율을 보고 룰을 고친 작업이다. 예전 하네스는 한 스트림을 잘라 학습·검증으로 썼으므로
그 서류가 곧 평가셋이었다.

| 바꾼 것 | 내용 |
|---|---|
| 생성 | 세트마다 생성기를 따로 만든다. `SyntheticGenerator(seed, split=DEV\|EVAL)` |
| 시드 | 평가셋은 `seed + 1,000,003`. **`+1` 이면 안 된다** — `--seed 42` 의 평가셋이 `--seed 43` 의 개발셋과 같아지고, 시드를 바꿔 평균 내는 순간(42~46) 분리가 조용히 무너진다 |
| 말뭉치 | 실물 말뭉치도 짝수·홀수로 나눈다. 같은 실물 B/L 이 양쪽에 나오면 분리가 반쪽이다 |
| 학습 | 모델도 개발셋만 본다. 조기 종료 검증도 개발셋 안에서 끝낸다 |
| 표기 | 표본이 `split` 을 들고 다니고, 평가 직전에 대조한다 |

마지막 항목이 이 작업에서 제일 중요하다. **개발셋 표본이 평가 보고에 섞여도 수치는
그럴듯하게 나온다 — 오히려 좋게 나온다.** 조용히 틀리는 종류라 사람이 눈으로 잡을
수 없고, 그래서 표본 자신이 출처를 들고 다녀야 한다.

**결과는 1절·3.1 에 반영했다.** 룰 단독 F1 0.9210 → **0.9124**. 하락분 0.0086 이
지금까지 본 서류를 다시 써서 얻고 있던 값이다. 크지 않다는 것이 좋은 소식이고,
그럼에도 모델 기여는 −0.0087 → **−0.0102** 로 더 내려갔다.

#### 17 — 두 비율에서 각각 보고한다

v2 10.3: "한쪽 비율만으로 산출한 수치는 해석을 왜곡한다."

균형 50% 와 실제 하자율 재현 70%(2장의 65~75% 중앙값) 두 평가셋을 만들고 **같은
모델**로 잰다. 조건마다 다시 학습하면 비율 효과와 학습 편차가 섞여 두 줄을 나란히
놓는 의미가 사라진다.

| 조건 | 룰 F1 | 룰+모델 F1 | 모델 기여 |
|---|---|---|---|
| 균형 50% | 0.9124 | 0.9022 | −0.0102 |
| 실제 70% | **0.9491** | 0.9470 | −0.0020 |

**실제 비율 쪽이 높은 것은 검출기가 좋아진 것이 아니다.** 하자가 많으면 정밀도가
저절로 오른다. 이 표를 한 줄만 떼어 인용하면 그 차이가 실력으로 읽히는데, 그게 10.3
이 경계한 왜곡이다. 목표 달성 판정도 **두 조건이 모두 넘어야** 성립하게 했다.

#### 20 — Critical 오탐률은 정밀도가 아니다

v2 5.3 수용 기준은 "Critical 등급의 오탐률 5% 이하"다. 정밀도로 대신할 수 없다 —
정밀도의 분모는 라벨 잡음이 섞인 `label` 이고, 여기서 물어야 하는 것은 **하자를
주입하지 않은 서류에 Critical 이 떴는가**다. 실무에서 대가를 치르는 것은 정상 서류가
반려되는 쪽이다.

**두 조건 모두 0.00%** 다(정상 300건 중 0건, 5시드 평균).

**이 값을 룰의 정확성으로 읽으면 안 된다.** 5.8 절의 '발화 0'과 같은 이유다 — 합성
생성기가 만드는 정상 서류가 깨끗하기 때문이기도 하다. 실물 말뭉치(5.9)에서 다시 재야
의미가 생기고, 그때는 0 이 아닐 가능성이 높다.

#### 남은 것

- **AUC·임계값 표(3.1 "그래서 모델을 어디에 쓰는가")는 분리 전 측정값이다.** 판정=룰 ·
  순위=모델 이라는 결론이 뒤집힐 값은 아니지만, 인용 전에 다시 재는 것이 맞다
- 회귀 테스트 14건 (`tests/test_defect_model.py`). 학습 프로토콜이 바뀌었으므로
  모델 artifact 도 개발셋으로 재학습해 커밋했다 — 5.8 절이 적었듯 재학습을 잊으면
  **로드는 성공하는데 값만 조용히 낡는다**

### 5.12 스캔 열화 재현 (18번)

v2 10.3 ④ 가 요구한 다섯 축을 3단계로 만든다 — 해상도 저하·기울기·노이즈·도장
겹침·접힘. `ocr/degrade.py` 이며 `preprocessor.py` 의 정확히 반대다. 저쪽은
지우고 이쪽은 만든다.

#### 축을 따로 거는 것이 요점이다

한 번에 다 걸면 "3단계에서 무너졌다"만 알고 **무엇 때문에** 무너졌는지를 모른다.
해상도 탓인지 도장 탓인지 구분되지 않으면 고칠 곳도 정해지지 않는다. 그래서
축별로 따로 걸고(`DegradationProfile.single`), 합성은 명시적으로 요청할 때만
한다(`uniform`). 원본(단계 0)은 표에 **한 번만** 넣는다 — 축마다 넣으면 같은
이미지가 다섯 번 나와 읽는 사람이 원본이 여럿인 줄 알게 된다.

#### 재현되지 않으면 재측정이 비교가 안 된다

v2 10.3 이 난수 시드 저장을 요구하는 이유가 이것이다. 축·단계마다 독립된 난수
흐름을 쓰되(`_rng`), 축을 구분하는 값으로 **`hash(axis)` 를 쓰면 안 된다.**
파이썬 문자열 해시는 `PYTHONHASHSEED` 로 프로세스마다 달라지므로, 같은 시드로
오늘과 내일 만든 이미지가 달라진다. 재현성이 존재 이유인 모듈이 조용히 무너지는
종류의 버그다. `zlib.crc32` 로 고정했고, 해시 시드를 바꿔 띄운 별도 프로세스와
결과를 대조하는 테스트가 이걸 지킨다.

#### 열화가 보정을 돕지 않게 한다

기울기를 걸 때 회전으로 생긴 여백을 검게 두면, 그 경계가 새 엣지가 되어
`_detect_skew_angle` 의 Hough 변환이 오히려 각도를 더 쉽게 찾는다. 열화가 보정을
도와주는 셈이라 `BORDER_REPLICATE` 로 가장자리를 늘려 채운다.

도장도 같은 이유로 **글자가 몰린 자리**에 놓는다. 여백에 찍으면 아무것도 가리지
않아 열화가 아니다. 접힘은 그늘만 넣지 않고 선 아래를 옆으로 민다 — 실제 접힌
종이는 글자가 어긋나고, 그 어긋남이 구역 좌표를 밀어내는 부분이며 여기서 보고
싶은 것도 그쪽이다.

#### 이 표를 정확도 근거로 읽지 말 것

2.1 절이 이미 한 번 겪은 종류의 과장이다. 합성 열화는 실제 복사기·팩스·스캐너가
만드는 열화와 다르다. 여기서 얻는 것은 **추출기의 상대적 내성**(어느 축에 약한가,
어느 단계에서 꺾이는가)이지 "실물에서 85% 를 넘는다"는 답이 아니다.

```bash
python -m ocr.degrade --image <서류.png>     # 축·단계별 추출 성적표 (PaddleOCR 필요)
```

테스트 17건. 단계가 실제로 세지는지(`단계가_올라가면_더_많이_망가진다`)와
재현성을 고정한다. "어느 축이 몇 % 떨어뜨리는가"는 환경과 원본에 달렸으므로
테스트에 박지 않았다.

### 5.13 수용 기준 실측 (19번) — 그리고 잴 수 없었던 것

`acceptance.py` 를 만들어 v2 5.1·5.3·5.4 의 완료 기준을 처음으로 쟀다.

| 기능 | 기준 | 목표 | 실측 | 판정 |
|---|---|---|---|---|
| F1 | 10페이지 추출 (텍스트) | 60초 | **67ms** | 통과 |
| F3 | 선적 1건 검증 | 10초 | **최대 8.1ms** | 통과 |
| F3 | 조문 근거 표시율 | 100% | **100%** | 통과 |
| F4 | 리포트 생성 | 15초 | **최대 7.7ms** | 통과 |
| F4 | 리포트 + PDF | 30초 | **최대 117ms** | 통과 |
| F4 | 조문 인용 + 조치 문장 보유율 | 100% | **100%** | 통과 |
| F4 | 리포트 수치와 판정 데이터 일치율 | 100% | **100%** | 통과 |
| F1 | 추출 정확도 (텍스트 PDF) | 95% | 참고값 83% | **미측정** |
| F1 | 추출 정확도 (스캔) | 85% | — | **미측정** |
| F1 | 근거 좌표 보유율 | 100% | — | **미측정** |
| F1 | 오추출 라우팅 재현율 | 90% | — | **미측정** |

**시간은 문제가 아니었다.** 목표 대비 세 자릿수 배수로 여유가 있다. 이건 좋은
소식이지만 동시에 **이 기준들이 우리 병목을 짚지 못했다**는 뜻이기도 하다.

#### 판정은 최댓값으로 한다

명세는 "선적 1건 검증 10초"라고 쓴다. **평균 10초는 절반이 넘긴다는 뜻이다.**
평균으로 보고하면 통과인데 사용자 절반이 기준 밖인 상태가 만들어지므로, 판정은
최댓값으로 하고 분포(p50·p95)를 함께 싣는다. 냉시작 1회는 따로 뗀다 — 모델
적재·폰트 등록은 요청당 비용이 아니라 프로세스당 비용이라, 섞으면 최댓값이
냉시작으로 정해져 정작 요청 비용을 못 본다.

리포트 시간은 **검증부터** 잰다. 이미 계산해 둔 verdict 를 재사용하면 0.000초가
나오는데, 그 숫자는 통과 판정을 주면서 아무것도 말하지 않는다. `/report` 가 실제로
하는 일(verify → build_report → 서사)을 재야 사용자가 기다리는 시간이 된다.

#### 미측정 넷은 이유가 서로 다르다

침묵으로 넘기지 않고 결과에 그대로 싣는다. 룰엔진이 평가불가를 1급 상태로 두는
것과 같은 이유다 — 빼면 "쟀고 통과했다"로 읽힌다.

- **추출 정확도(텍스트 PDF)** — 잰 레이아웃이 `REGIONS` 가 교정된 바로 그 서식이라
  나온 값이 **상한**이다. 수용 기준의 답으로 쓸 수 없다
- **추출 정확도(스캔)** — 실물 스캔 말뭉치가 없다. 2.1 절이 이미 확인했듯 합성
  이미지 1장으로는 모델 구성 여섯이 전부 만점이라 아무것도 구분되지 않는다
- **오추출 라우팅 재현율** — 수단은 18번으로 생겼다. 다만 PaddleOCR 과 원본
  이미지가 필요해 이 측정에 넣지 않았다. 넣으면 수용 기준 측정 전체가 OCR 설치와
  장당 10초에 묶인다
- **근거 좌표 보유율** — 아래가 이번 측정의 실제 수확이다

#### 근거 좌표는 실물이 와도 못 잰다 — 구조가 없다

**`BLFields` 가 좌표를 들고 나오지 않는다.** `confidence`·`provenance`·`raw_regions`
는 남는데 bbox 는 파서 안에서 버려진다. 즉 v2 5.1 의 "근거 좌표 보유율 100%" 는
데이터가 부족해서 못 잰 것이 아니라 **애초에 담을 그릇이 없다.**

이건 수용 기준 하나가 미달인 문제로 끝나지 않는다. 모노레포 DB 스키마의
`field_value` 는 자동 추출 값(`RULE`·`OCR_LLM`)에 좌표를 **CHECK 제약으로** 요구한다
— "추정 생성 금지" 규칙을 애플리케이션이 아니라 DB 가 강제한다. 지금 구조로는
그 테이블에 한 행도 넣을 수 없다.

> 측정 도구를 만든 값이 여기서 나왔다. 재보기 전에는 이 항목이 "실물 없어서
> 미측정"으로 보였고, 실물만 오면 풀리는 줄 알았다.

```bash
python -m acceptance --count 100          # 위 표가 그대로 나온다
python -m acceptance --llm                # 서사를 LLM 으로 생성해 잰다 (네트워크에 묶인다)
```

테스트 16건. 성능 임계값은 환경에 따라 달라지므로 박지 않고, **도구가 정직한가**를
고정한다 — 미측정이 통과로 집계되지 않는지, 판정이 최댓값으로 나는지.

재추정 시 아래를 다시 돌려 1·3절 수치를 갱신할 것.

```bash
cd aiService
# 의존성은 venv 에 있다. 없으면: python -m venv .venv && .venv/Scripts/python -m pip install -r requirements.txt
# 아래 `python` 은 `.venv/Scripts/python` (Windows) / `.venv/bin/python` (그 외) 을 가리킨다.

# 코드량 · 테스트
find . -name "*.py" -not -path "./__pycache__/*" -not -path "./.venv/*" | xargs wc -l | tail -1
python -m pytest tests/ -q

# 수용 기준 (5.13 의 표가 그대로 나온다)
python -m acceptance --count 100

# 스캔 열화 단계별 추출 성적 (5.12) — PaddleOCR 과 원본 이미지가 필요하다
python -m ocr.degrade --image <서류.png>

# 룰 카탈로그
python -c "import yaml; d=yaml.safe_load(open('ruleEngine/rules.yaml',encoding='utf-8')); print(len(d['rules']))"

# 3열 비교표 포함 전체 리포트 (3.1 절의 표가 그대로 나온다)
python -m mlModel.evaluate --count 2000

# F1-score · 재현율 · 특징 중요도 (5초)
python -c "
from mlModel import evaluate
r = evaluate(count=2000, seed=42)
for n, m in (('룰만', r.rules_only), ('룰+모델', r.rules_plus_model)):
    p = m.true_positive/max(1, m.true_positive+m.false_positive)
    rc = m.true_positive/max(1, m.true_positive+m.false_negative)
    print(f'{n}: F1={2*p*rc/(p+rc):.4f}')
print(r.per_defect_recall)
# 3.1 표는 비중(%)이다. 원값은 gain 이므로 정규화해서 읽을 것.
fi = r.feature_importance; tot = sum(fi.values())
for k, v in sorted(fi.items(), key=lambda x: -x[1]):
    print(f'{k:<30} {v/tot*100:5.1f}%')
"
```

유형별 재현율은 시드 하나로 보면 흔들린다(`missing_field` 은 0.71~0.78 범위). 3.2 처럼 유형별 수치를 인용할 때는 여러 시드 평균을 쓸 것.

```bash
python -c "
from mlModel import evaluate
import statistics as st
rs = [evaluate(count=2000, seed=s, train_model=False) for s in (1, 7, 42, 123, 2026)]
for kind in rs[0].per_defect_recall:
    print(f'{kind:<22} {st.mean(r.per_defect_recall[kind] for r in rs):.4f}')
"
```

**1절 표는 5개 시드(42~46) 평균이다.** 두 비율 조건과 Critical 오탐률까지 한 번에 뽑는다.

```bash
python -c "
from mlModel import evaluate
import statistics as st
rs = [evaluate(count=2000, seed=s) for s in (42, 43, 44, 45, 46)]
avg = lambda f: st.mean(f(r) for r in rs)
for name, pick in (('균형 50%', lambda r: r), ('실제 70%', lambda r: r.realistic)):
    print(f'{name}  룰만 F1 {avg(lambda r: pick(r).rules_only.f1):.4f}'
          f'  룰+모델 F1 {avg(lambda r: pick(r).rules_plus_model.f1):.4f}'
          f'  기여 {avg(lambda r: pick(r).model_contribution):+.4f}'
          f'  Critical 오탐 {avg(lambda r: pick(r).critical_false_alarm_rate):.2%}')
"
```

> **개발셋 수치를 인용하지 말 것.** `evaluate()` 가 보고하는 값은 전부 평가셋에서
> 나오고, 개발셋은 모델 학습에만 쓴다(5.11). 룰을 고치며 확인할 때도 평가셋을 열어
> 맞추면 분리가 무의미해진다 — 그럴 때는 `SyntheticGenerator(seed, split=DEV)` 로
> 직접 뽑아서 볼 것.
