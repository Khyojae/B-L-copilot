## M-1. "검증 실행" 버튼 활성 조건

### 문제

기획안 세 곳의 서술이 서로 다릅니다.

| 근거 | 내용 |
|---|---|
| 5.1 (F1 표) | 필수 확인 필드 있으면 **검증 실행 차단** |
| 5.3 (F3 예외) | 필수 확인 필드 남은 채 실행하면 해당 룰 **판정 보류** |
| 5.8 (상태 게이트) | 사유 기록하면 **강제 진행 가능** |

세 개를 그대로 합치면 말은 되는데, 정확히 이렇게 적힌 곳이 없어서 FE가 버튼 하나의 동작을 세 문장 조합해서 유추해야 하는 상태입니다.

### 지금 임시로 구현한 규칙

> 필수 확인 필드가 1개 이상이면 검증 실행 버튼은 **비활성**.
> 단 "사유 기록 후 강제 실행"을 별도 경로로 제공하며,
> 이 경우 해당 필드 관련 룰은 **DEFERRED**로 표기하고 확률 산출에서 제외.
> 보류 건수는 리포트에 명시.

`src/pages/S3Draft/VerifyBar.tsx`, `src/constants/domain.ts`의 `canTransitionToVerified()`에 이 규칙으로 이미 만들어져 있습니다. 목데이터로 4개 선적 전부 이 규칙으로 동작 확인했습니다 (판정 목록·리스크 요약·"필수 확인 N건" 표시 전부 연동됨).

### 확인 요청

- [ ] 위 통합 규칙으로 **확정**해도 되는지
- [ ] 다르다면, 정확히 어떤 조건이어야 하는지 (예: 강제 실행에 승인 권한이 따로 필요한지, 사유 기록 최소 글자수 등)

## M-2. 사용자가 직접 수정한 필드값을 어떻게 취급할지

### 문제

기획안에 없는 부분입니다. `FieldRow`에서 사용자가 값을 클릭해서 직접 타이핑으로 고쳤을 때, 이 값을 신뢰도 몇 등급으로 볼지가 정의돼 있지 않습니다.

이게 걸리는 이유 — 규약 원칙 중 "근거 없는 값은 표시하지 않는다"가 있습니다. 사용자가 직접 고친 값은 **원문 근거 좌표(bbox)가 원래 값 위치를 가리키는 채로 남아 있고, 화면에 보이는 값만 바뀝니다.** 이게 "확정"이라고 표시해도 괜찮은지가 애매합니다.

### 지금 임시로 구현한 규칙

> 사용자가 직접 타이핑해서 수정하면, 등급과 무관하게 **CONFIRMED(확정)**로 취급한다.

근거: "사람이 직접 확인하고 고친 값이니 AI 추출보다 오히려 신뢰할 만하다"는 해석.

> ⚠ 구현 위치가 바뀌었습니다 (2026-08-18).
> 전에는 `src/pages/S3Draft/fieldEditing.ts`에 있었지만, S1 대시보드·S4 검증
> 결과도 같은 계산을 써야 해서 `src/shared/shipmentStats.ts`의
> `effectiveGradeOf()`로 옮겼습니다. 규칙 자체는 그대로입니다.

### 확인 요청

- [ ] 위 해석(직접 수정 = 무조건 확정)으로 **확정**해도 되는지
- [ ] 아니라면, 어떤 기준이어야 하는지 (예: 직접 수정값도 별도 검증 단계를 거쳐야 하는지, 등급을 한 단계만 올려주는 식인지)

## M-2 추가 논의 (2026-08-18) — "직접 입력"과 "후보 중 선택"은 다른 행동입니다

### 문제

값 충돌 필드(`conflict_flag: true`)에 **후보 선택 UI**를 만들면서 드러난 문제입니다.
지금 `isEditedField()`가 **두 가지 다른 행동을 같게 묶고 있습니다.**

| | 직접 입력 | 후보 중 선택 |
|---|---|---|
| 무엇을 하나 | 사람이 새 값을 써넣음 | 원문에서 이미 읽어낸 값 중 하나를 고름 |
| 원문 근거 | 없음 (bbox는 옛 위치를 가리킨 채로 남음) | 그 후보의 bbox·출처·신뢰도가 그대로 있음 |
| 인식 품질 | 해당 없음 | 고른다고 원문 인식 품질이 좋아지지 않음 |

같게 묶어두니 실제로 두 가지 문제가 났습니다.

**(1) 원본과 같은 값을 고르면 아무 반응이 없었습니다.**
`isEditedField()`가 "원본 값과 다른가"로 판단하는데, `port_of_loading`의 원본 값이 이미 `BUSAN`이라 BUSAN을 골라도 "안 고친 것"이 됐습니다. 사용자는 확정 동작을 했는데 화면이 그대로였습니다.

**(2) 낮은 신뢰도를 고르면 오히려 등급이 올라갔습니다.**
INCHEON(선적요청서, 0.71)을 고르면 "수정했다"로 처리돼 확정이 됐습니다. BUSAN(신용장, 0.90)을 고른 것과 결과가 같아집니다. 낮은 쪽을 고르는 게 더 위험한 선택인데, 시스템이 그 위험을 감추는 셈입니다.

### 지금 임시로 구현한 규칙 (2026-08-18 반영)

> **후보 선택은 "값 수정"이 아니라 "충돌 해소"로 따로 취급한다.**
> 어느 후보를 고르든 충돌은 해소되고(`conflict_flag: false`),
> 등급은 **그 후보가 원래 갖고 있던 신뢰도**를 그대로 따른다.

- BUSAN(신용장, 0.90) 선택 → **확정**
- INCHEON(선적요청서, 0.71) 선택 → **확인 권고**

`src/shared/shipmentStats.ts`의 `resolveConflicts()`에 구현했습니다. 고른 후보의 값·정규화값·bbox·출처·신뢰도를 그대로 승계하고 `conflict_flag`만 내립니다. 화면(`CandidateChooser`)에도 M-1과 같은 방식으로 "M-2 미결" 표시를 남겨뒀습니다.

### 확인 요청

- [ ] **직접 입력과 후보 선택을 나누는 것**이 맞는지
- [ ] 후보 선택 시 "그 후보의 원래 신뢰도를 따른다"가 맞는지.
      아니면 사람이 골랐다는 사실 자체로 확정으로 올려야 하는지
- [ ] 후보를 골라도 여전히 "확인 권고"로 남으면, 검증 실행은 가능하지만
      리포트에 미확인 항목으로 기재됩니다. 이게 의도한 동작인지
- [ ] 후보 선택 **되돌리기(선택 취소)** 를 넣어뒀는데, 이대로 유지할지
      (고른 뒤 "선택 취소"를 누르면 다시 충돌 상태 = 필수 확인으로 돌아갑니다)

## 왜 지금 확정이 필요한지

- **VerifyBar(검증 실행 버튼)**가 M-1에 걸려 있어서, 화면 상단에 "임시안입니다" 배너가 계속 떠 있는 상태로 시연/심사를 맞이하게 됩니다.
- 두 규칙 다 **하자 확률 계산(DefectPrediction)**과 직결됩니다 — 어떤 필드를 DEFERRED로 뺄지, 사용자 수정값을 확률 계산에 어떻게 반영할지가 이 규칙에 달려 있어서, 이 프로젝트의 핵심 지표(F1 0.85 목표)에도 영향을 줍니다.

확정되는 대로 코드 반영은 바로 가능합니다 (로직이 이미 한 곳에 모여 있어서 그 부분만 고치면 됨).
